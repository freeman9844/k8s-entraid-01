온프레미스 Kubernetes에서 Client Secret으로 Foundry Models 호출하기

Entra 앱 등록에서 Client Secret을 발급해 Kubernetes Secret에 저장하고, 파드가 이를 환경변수로 받아 Azure 액세스 토큰을 얻은 뒤 Foundry 모델을 호출합니다.

Client Secret 구성 가장 중요양쪽

신뢰 관계는 앱 ID + Client Secret 값으로 성립합니다. Entra는 Secret의 해시만 보관하고, 원문은 발급 시점에 한 번만 보여 줍니다.

구성 요소위치 / 값
Client Secret 값Kubernetes Secret wif-secret (key: client-secret) → 파드 환경변수 AZURE_CLIENT_SECRET
앱 등록 / 서비스 주체Entra ID. 서비스 주체에 Foundry 역할 부여
유효기간발급 시 지정(랩: 1년). 만료되면 인증 실패
필수 환경변수AZURE_CLIENT_ID, AZURE_TENANT_ID, AZURE_CLIENT_SECRET

Secret 값을 코드, 이미지, Git, 로그에 남기지 마세요. 랩 스크립트도 값을 출력하지 않고 .state 파일에만 저장했습니다.

Azure 구성 Azure

bash
# 1) 앱 등록 + 서비스 주체
APP_ID=$(az ad app create --display-name app-wif-secret --query appId -o tsv)
az ad sp create --id $APP_ID

# 2) Client Secret 발급 (값은 이 시점에만 확인 가능)
SECRET=$(az ad app credential reset --id $APP_ID --append --display-name demo --years 1 --query password -o tsv)

# 3) Foundry 호출 권한 (Foundry 는 disableLocalAuth=true 로 API Key 차단)
az role assignment create --assignee-object-id $(az ad sp show --id $APP_ID --query id -o tsv) \
  --assignee-principal-type ServicePrincipal \
  --role "Cognitive Services OpenAI User" --scope $FOUNDRY_ID

자동화: scripts/s1-create-app-secret.sh. --append를 빼면 앱의 기존 자격 증명이 모두 교체됩니다.

앱 등록은 리소스 그룹 밖(테넌트)에 생성됩니다. 정리할 때 az ad app delete가 별도로 필요합니다(99-cleanup.sh가 처리).

Kubernetes 구성 온프레미스

bash
kubectl create namespace wif-demo
kubectl -n wif-demo create secret generic wif-secret --from-literal=client-secret="$SECRET"
yaml
env:
  - {name: AZURE_CLIENT_ID, value: "<앱 등록 appId>"}
  - {name: AZURE_TENANT_ID, value: "<테넌트 ID>"}
  - name: AZURE_CLIENT_SECRET
    valueFrom:
      secretKeyRef: {name: wif-secret, key: client-secret}

env는 컨테이너 항목 안에 넣습니다.

테스트에 사용한 전체 매니페스트 (Deployment)

검증에 사용한 매니페스트입니다(k8s/deploy-secret.yaml.tpl).

yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: secret-call
  namespace: wif-demo
spec:
  replicas: 1
  selector:
    matchLabels:
      app: secret-call
  template:
    metadata:
      labels:
        app: secret-call
    spec:
      containers:
        - name: demo
          image: python:3.12-slim
          command: ["sh", "-c", "pip install -q --disable-pip-version-check azure-identity openai && python /app/demo_secret.py; sleep infinity"]
          env:
            - name: AZURE_CLIENT_ID
              value: "<앱 등록 appId>"
            - name: AZURE_TENANT_ID
              value: "<테넌트 ID>"
            - name: AZURE_CLIENT_SECRET
              valueFrom:
                secretKeyRef:
                  name: wif-secret
                  key: client-secret
            - name: FOUNDRY_ENDPOINT
              value: "https://<foundry 이름>.openai.azure.com"
            - name: FOUNDRY_DEPLOYMENT
              value: "gpt-5.4-mini"
            - name: TOKEN_RETRIES
              value: "6"
          volumeMounts:
            - name: app
              mountPath: /app
      volumes:
        - name: app
          configMap:
            name: secret-demo-app   # demo_secret.py 를 담은 ConfigMap

FOUNDRY_*, TOKEN_RETRIES(Entra 전파 대기용 토큰 요청 재시도 횟수), ConfigMap, 끝의 sleep infinity(결과 로그 확인용)는 테스트 데모 앱용입니다. 실제 앱에는 환경변수 3개만 필요합니다.

Kubernetes Secret은 기본적으로 base64일 뿐입니다. etcd 암호화(--secrets-encryption)와 Secret 읽기 RBAC 최소화를 반드시 적용하세요.

애플리케이션 코드 온프레미스

코드는 DefaultAzureCredential만 사용합니다. 환경변수 3개가 있으면 EnvironmentCredential이 Client Secret 방식을 자동 선택합니다.

갱신과 보호 미검증/참고용

  • 갱신: 앱 등록에는 Client Secret을 여러 개 등록할 수 있습니다. 새 Secret을 --append로 발급 → Kubernetes Secret 덮어쓰기 → rollout restart → 새 Secret으로 호출 확인 후 옛 Secret 삭제(az ad app credential delete --id $APP_ID --key-id <keyId>) 순서로 무중단 교체합니다. 이번 랩에서는 갱신 절차를 인증서 방식으로만 검증했습니다.
  • 만료 관리: Secret은 만료되면 즉시 인증이 실패합니다. 만료일을 모니터링하고 짧은 수명(예: 90일~1년)과 자동 교체를 구성하세요.
  • Key Vault: 가능하면 Secret 값을 Key Vault에 두고 CSI Driver로 마운트하세요. 단 Key Vault 접근에 필요한 자격 증명은 별도로 보호해야 합니다.
  • 접근 통제: get secret 권한과 exec 권한을 최소화하고, etcd 암호화와 감사 로그를 켜세요.
