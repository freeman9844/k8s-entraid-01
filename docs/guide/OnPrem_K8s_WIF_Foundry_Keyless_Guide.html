온프레미스 클러스터에는 Azure 관리 ID(IMDS)가 없습니다. 대신 클러스터가 발급한 ServiceAccount 토큰을 Entra ID가 신뢰하도록 등록해, 비밀 값 없이 Azure 액세스 토큰을 받습니다.

먼저 읽기: 무엇을 만들고, 왜 필요한가요?

Azure 안의 VM·AKS는 관리 ID로 토큰을 받지만, 온프레미스 파드는 그럴 수 없어 보통 Client Secret이나 인증서, API Key를 Secret에 저장합니다. 이 가이드는 그 대신 클러스터가 서명한 토큰을 Entra ID가 직접 검증하게 해 저장할 비밀을 없앱니다. 유출·만료·회전 관리가 필요한 값이 없어집니다.

용어이 구성에서 하는 일
Workload Identity Federation (WIF)외부 ID 공급자(여기서는 온프레미스 Kubernetes)가 발급한 토큰을 Entra ID가 신뢰하고 Azure 액세스 토큰으로 교환해 주는 기능
OIDC Issuer“이 토큰은 내 클러스터가 서명했다”를 증명하는 공개 주소. Entra가 여기서 discovery 문서와 JWKS(공개키)를 읽음
UAMI (사용자 할당 관리 ID)파드가 가장하게 될 Azure 쪽 ID. Foundry 권한을 가짐. VM이나 클러스터에 붙이는 것이 아니라 federated credential의 대상일 뿐임
Federated credentialUAMI에 붙이는 신뢰 규칙. issuer + subject + audience가 모두 일치하는 토큰만 교환
Projected SA 토큰파드 매니페스트의 serviceAccountToken 볼륨. audience를 api://AzureADTokenExchange로 지정한 짧은 수명 토큰을 kubelet이 파일로 넣고 갱신함. 앱은 DefaultAzureCredential만 호출

비용: Foundry 모델 호출과 issuer 호스팅(Storage 등)에 비용이 발생합니다. 랩 리소스는 사용 후 리소스 그룹을 삭제하세요.

★ WIF 신뢰 체인: 값 4개가 한 글자도 틀리지 않고 이어져야 합니다

“온프레미스 클러스터가 서명한 토큰”과 “Entra의 UAMI에 등록한 규칙”이 같은 값을 가리켜야 합니다. 아래 표의 같은 행은 문자 단위로 동일해야 하며 틀리면 Entra가 교환을 거부합니다. 3~6단계가 이 연결을 하나씩 만듭니다.

왜 하나요? 파드가 최종적으로 가장할 ID(UAMI), 호출 대상(Foundry), Entra가 읽을 issuer 호스팅 공간을 만듭니다.

RG=rg-wif-demo; LOC=eastus2; SUFFIX=$RANDOM
SUB=$(az account show --query id -o tsv)
TENANT_ID=$(az account show --query tenantId -o tsv)      # 7단계 AZURE_TENANT_ID
FOUNDRY=foundry-wif-$SUFFIX; MODEL=gpt-5.4-mini; MODEL_VER=2026-03-17   # 지역에서 GA인 모델·버전으로 변경
az group create -n $RG -l $LOC

# 1) UAMI: 파드가 가장할 Azure ID (비밀 없음)
az identity create -g $RG -n id-wif-demo
CLIENT_ID=$(az identity show -g $RG -n id-wif-demo --query clientId -o tsv)       # 7단계 AZURE_CLIENT_ID
PRINCIPAL_ID=$(az identity show -g $RG -n id-wif-demo --query principalId -o tsv)

# 2) Foundry(AIServices) 리소스: API Key 비활성(disableLocalAuth=true) → keyless만 가능
#    (az cognitiveservices account create 는 PublicNetworkAccess 오류가 날 수 있어 ARM PUT 사용)
az rest --method put -o none \
  --url "https://management.azure.com/subscriptions/$SUB/resourceGroups/$RG/providers/Microsoft.CognitiveServices/accounts/$FOUNDRY?api-version=2025-06-01" \
  --body "{\"location\":\"$LOC\",\"kind\":\"AIServices\",\"sku\":{\"name\":\"S0\"},\"properties\":{\"customSubDomainName\":\"$FOUNDRY\",\"publicNetworkAccess\":\"Enabled\",\"disableLocalAuth\":true}}"
until [ "$(az cognitiveservices account show -g $RG -n $FOUNDRY --query properties.provisioningState -o tsv)" = Succeeded ]; do sleep 10; done
FOUNDRY_ID=$(az cognitiveservices account show -g $RG -n $FOUNDRY --query id -o tsv)
az cognitiveservices account deployment create -g $RG -n $FOUNDRY --deployment-name $MODEL \
  --model-name $MODEL --model-version $MODEL_VER --model-format OpenAI --sku-name GlobalStandard --sku-capacity 10
echo "https://$FOUNDRY.openai.azure.com"                  # 7단계 FOUNDRY_ENDPOINT, 배포 이름은 $MODEL

# 3) UAMI에 Foundry 호출 권한 (데이터 평면 역할, 최소 권한)
az role assignment create --assignee-object-id $PRINCIPAL_ID --assignee-principal-type ServicePrincipal \
  --role "Cognitive Services OpenAI User" --scope $FOUNDRY_ID

# 4) issuer 호스팅: Blob 정적 웹사이트 (다른 공개 HTTPS 호스팅도 가능)
az storage account create -g $RG -n stwif$SUFFIX -l $LOC --sku Standard_LRS --allow-shared-key-access false
SA_ID=$(az storage account show -g $RG -n stwif$SUFFIX --query id -o tsv)
az role assignment create --assignee-object-id $(az ad signed-in-user show --query id -o tsv) \
  --assignee-principal-type User --role "Storage Blob Data Contributor" --scope $SA_ID   # 업로드 계정 (전파 수 분)
az storage blob service-properties update --account-name stwif$SUFFIX --static-website --index-document index.html --auth-mode login -o none
ISSUER_URL=$(az storage account show -g $RG -n stwif$SUFFIX --query primaryEndpoints.web -o tsv | sed 's:/*$::')
UAMI 대신 앱 등록?Entra 앱 등록(App registration)에도 federated credential을 만들 수 있습니다. 이 가이드는 별도 비밀·인증서 관리가 없고 Azure RBAC로 권한을 주기 쉬운 UAMI를 사용합니다.
ISSUER_URL끝에 슬래시를 붙이지 않은 값으로 통일합니다. 이후 3단계 플래그와 6단계 federated credential에 동일하게 사용합니다.
issuer 호스팅의 대안사내 공개 웹서버/CDN, GitHub Pages 등 Entra가 인터넷에서 읽을 수 있는 공인 HTTPS 주소면 됩니다. 사설 주소(사내 전용 DNS)는 Entra가 접근할 수 없어 사용할 수 없습니다.

Storage 공개 접근이 구독/관리그룹 정책으로 Disabled가 강제되면 issuer를 열 수 없습니다(4단계 경고 참고).

이후 단계에서 같은 셸의 변수(RG, SUFFIX, ISSUER_URL, CLIENT_ID, TENANT_ID)를 씁니다. 셸을 닫았다면 값을 다시 설정하세요. 스토리지 역할 전파가 늦으면 정적 웹사이트 설정이 실패할 수 있으니 몇 분 뒤 다시 실행합니다. Foundry 역할(Cognitive Services OpenAI User) 전파는 더 오래 걸려 랩에서 약 15분이었으며, 7단계 호출이 401이면 기다렸다가 재시도합니다. Windows Git Bash에서는 /subscriptions/… 같은 인자가 경로로 변환되어 --scope가 깨지므로 export MSYS_NO_PATHCONV=1을 먼저 실행하세요(PowerShell·WSL·Linux·macOS는 불필요).

완료 기준: echo $ISSUER_URL이 https://stwif…web.core.windows.net 형태로 출력되고 UAMI·Foundry·RBAC가 준비됩니다.

클러스터 API 서버에 OIDC issuer 지정 WIF 핵심 ① 온프레미스

왜 하나요? 클러스터가 발급하는 ServiceAccount 토큰의 iss가 Entra가 접근할 수 있는 공개 URL이 되게 합니다. 기본값(https://kubernetes.default.svc.cluster.local 등)은 외부에서 접근할 수 없어 WIF가 성립하지 않습니다.

🔑 WIF 설정 포인트강조된 줄 service-account-issuer 값 = 토큰의 Issuer = 6단계 --issuer. 끝에 /를 붙이거나 http로 쓰는 등 한 글자만 달라도 AADSTS700211이 납니다.
--service-account-issuer토큰 iss 값. 6단계 federated credential의 issuer와 완전히 같아야 함. 클러스터에 필요한 변경은 이 플래그 1개뿐
--service-account-jwks-uri지정하지 않습니다. 이 플래그는 API 서버가 내놓는 discovery 문서의 jwks_uri만 바꿉니다. 이 가이드는 discovery 문서를 4단계에서 직접 작성해 올리므로 필요 없습니다(랩 검증)

3-0. 변경 전 점검 (모든 배포판 공통)

# 1) 현재 issuer 기록 (롤백 시 필요). kubeadm 기본값: https://kubernetes.default.svc.cluster.local
kubectl get --raw /.well-known/openid-configuration

# 2) 변경 전 기존 토큰 하나 확보 (변경 후에도 유효한지 확인용)
kubectl -n default create token default --duration=3h > /tmp/old.tok

# 3) kubeadm: 매니페스트 백업은 manifests 디렉터리 "밖"에 둡니다 (안에 두면 kubelet이 static pod로 해석)
sudo cp /etc/kubernetes/manifests/kube-apiserver.yaml /root/kube-apiserver.yaml.bak
kubectl -n kube-system get cm kubeadm-config -o yaml | sudo tee /root/kubeadm-config.bak.yaml >/dev/null

kubeadm 랩 검증

컨트롤 플레인 노드의 /etc/kubernetes/manifests/kube-apiserver.yaml command에서 기존 issuer 줄을 새 공개 URL(첫 번째) + 기존 issuer(두 번째)로 바꿉니다. 저장하면 kubelet이 API 서버를 자동 재시작합니다(랩: 약 40초 동안 API 불가, 기존 파드는 계속 실행).

    - --service-account-issuer=<ISSUER_URL>
    - --service-account-issuer=https://kubernetes.default.svc.cluster.local   # 기존 값(검증 전용)

OIDC 메타데이터 공개 WIF 핵심 ② 온프레미스 → Azure

왜 하나요? Entra ID는 토큰의 iss 주소로 직접 접속해 서명 검증용 공개키를 가져옵니다. 클러스터 서명 키의 공개키만 JWKS로 만들어 공개 호스팅에 올립니다. 개인키는 클러스터 밖으로 나가지 않습니다.

🔑 WIF 설정 포인트강조된 줄: issuer는 3단계 issuer와 동일해야 하고, jwks_uri는 Entra가 공개키를 가져가는 공개 주소여야 합니다(내부 주소 불가). 업로드 경로는 .well-known/openid-configuration, openid/v1/jwks로 고정입니다.

4-1. 공개키(JWKS) 확보

API 서버가 서명 공개키 목록을 그대로 제공하므로 한 줄이면 됩니다. 서명 키 파일 경로나 배포판을 몰라도 됩니다.

kubectl get --raw /openid/v1/jwks > jwks.json

/.well-known/openid-configuration은 jwks_uri가 클러스터 내부 주소라 그대로 올리면 안 되고 아래 4-2의 문서를 직접 작성합니다. 가져오는 것은 jwks.json뿐입니다.

키 회전 시 JWKS에 이전 키와 새 키가 함께 있어야 이미 발급된 토큰이 계속 검증됩니다. 회전 때마다 이 단계를 다시 수행하는 운영 절차를 마련하세요(8단계).

4-2. discovery 문서 작성 · 업로드 경로

/.well-known/openid-configurationEntra가 가장 먼저 읽는 문서. issuer가 토큰의 iss와 같아야 함
/openid/v1/jwks서명 검증용 공개키 목록. 토큰 헤더의 kid와 일치하는 키가 있어야 함
{
  "issuer": "https://stwif<SUFFIX>.z20.web.core.windows.net",
  "jwks_uri": "https://stwif<SUFFIX>.z20.web.core.windows.net/openid/v1/jwks",
  "response_types_supported": ["id_token"],
  "subject_types_supported": ["public"],
  "id_token_signing_alg_values_supported": ["RS256"]
}
# discovery 문서 생성 (파일명은 확장자 없이 openid-configuration)
cat > openid-configuration <<EOF
{
  "issuer": "$ISSUER_URL",
  "jwks_uri": "$ISSUER_URL/openid/v1/jwks",
  "response_types_supported": ["id_token"],
  "subject_types_supported": ["public"],
  "id_token_signing_alg_values_supported": ["RS256"]
}
EOF

# 두 파일 모두 Content-Type: application/json
az storage blob upload --account-name stwif$SUFFIX --auth-mode login -c '$web' \
  -f openid-configuration -n .well-known/openid-configuration --content-type application/json --overwrite -o none
az storage blob upload --account-name stwif$SUFFIX --auth-mode login -c '$web' \
  -f jwks.json -n openid/v1/jwks --content-type application/json --overwrite -o none

실제 토큰의 iss·kid가 공개된 값과 같은지 확인합니다. 참고용 스크립트 03-publish-oidc.sh는 이 대조(scripts/lib/check_jwks.py)까지 자동으로 수행합니다.

curl -fsS $ISSUER_URL/.well-known/openid-configuration
curl -fsS $ISSUER_URL/openid/v1/jwks
kubectl -n default create token default --audience api://AzureADTokenExchange   # iss / kid 비교 대상

완료 기준: 토큰의 iss가 ISSUER_URL과 같고, 토큰 헤더의 kid가 공개 JWKS의 keys[].kid 중 하나와 같습니다. (참고용 스크립트 출력: OK: 토큰의 iss/kid 가 공개된 issuer/JWKS 와 일치합니다)

정책 때문에 업로드/접근이 막히면: 일부 구독은 정책(modify 효과)이 Storage의 publicNetworkAccess를 Disabled로 강제하고 CLI로 바꿔도 되돌립니다. 랩 환경에서는 관리그룹의 MCAPSGovDeployPolicies가 원인이었고(아래 목록에서 이름으로 찾음), 리소스 그룹 범위 정책 예외 생성 → 1분 대기 → 공개 접근 활성화 후 통과했습니다.

파드에 토큰 주입: 매니페스트로 WIF 핵심 ③ 온프레미스

왜 하나요? 파드가 Entra에 제시할 토큰(audience api://AzureADTokenExchange인 SA 토큰)과 접속 정보를 파드 안에 넣어야 합니다. 파드 매니페스트에 직접 적어 클러스터에 별도 구성요소를 설치하지 않습니다. 랩에서 이 방식으로 검증했습니다.

🔑 WIF 설정 포인트토큰 audience, UAMI(AZURE_CLIENT_ID), 테넌트(AZURE_TENANT_ID), 토큰 파일 경로(AZURE_FEDERATED_TOKEN_FILE)가 WIF 연결에 쓰입니다. 7단계 매니페스트의 강조된 줄과 같습니다.

파드 매니페스트에 넣는 것

projected 볼륨serviceAccountToken: audience: api://AzureADTokenExchange, expirationSeconds: 3600, path: azure-identity-token. Audience 연결 고리. kubelet이 만료 전 자동 갱신
AZURE_CLIENT_IDUAMI client ID
AZURE_TENANT_IDEntra 테넌트 ID
AZURE_AUTHORITY_HOSThttps://login.microsoftonline.com/
AZURE_FEDERATED_TOKEN_FILE볼륨을 마운트한 경로의 토큰 파일. 이 가이드는 /var/run/secrets/azure/tokens/azure-identity-token

SDK(DefaultAzureCredential → WorkloadIdentityCredential)가 위 환경변수 4개를 읽어 토큰을 교환합니다. 값은 모두 비밀이 아닙니다(ID와 경로). 토큰은 짧은 수명의 파드 전용 값이며 Secret 오브젝트로 저장되지 않습니다. 전체 YAML은 7단계에 있습니다.

완료 기준: 클러스터 변경은 3단계 플래그 1개뿐입니다.

Federated credential 생성 WIF 핵심 ④ · 가장 중요 Azure

왜 하나요? “어느 issuer의 어느 ServiceAccount가 보낸 토큰을 이 UAMI로 인정할지”를 Entra에 등록합니다. 온프레미스 클러스터가 Azure 리소스에 접근할 수 있는 근거가 이 규칙 하나입니다.

🔑 WIF 설정 포인트: 신뢰 체인의 핵심강조된 세 줄 --issuer(3단계 값) · --subject(7단계 네임스페이스·SA 이름) · --audiences(7단계 projected 볼륨 audience)가 토큰의 값과 모두 일치해야 Entra가 토큰을 교환해 줍니다.
az identity federated-credential create \
  -g $RG --identity-name id-wif-demo -n fic-onprem-wif-sa \
  --issuer   "$ISSUER_URL" \
  --subject  "system:serviceaccount:wif-demo:wif-sa" \
  --audiences api://AzureADTokenExchange
파라미터값과 의미
--issuerISSUER_URL. 토큰 iss와 문자 단위로 동일(끝 슬래시 없음). 다르면 AADSTS700211
--subjectsystem:serviceaccount:<네임스페이스>:<SA 이름>. 정확히 일치(와일드카드 불가)
--audiencesapi://AzureADTokenExchange. 토큰 aud와 일치해야 함

subject를 SA 하나로 제한하는 이유 (최소 권한)

subject를 wif-sa로 고정하면 같은 클러스터의 다른 ServiceAccount는 UAMI 권한을 쓸 수 없습니다. 랩에서 wif-other-sa 파드에 같은 AZURE_CLIENT_ID를 줘도 Entra가 AADSTS700213으로 거부함을 확인했습니다. 워크로드마다 UAMI와 federated credential을 분리하세요.

등록 직후 전파에 수 분 걸릴 수 있습니다. 참고용 스크립트(05-federate.sh)는 자동 재시도합니다. 클러스터를 여러 개 운영한다면 클러스터마다 issuer가 다르므로 federated credential을 각각 만들어야 합니다(UAMI당 한도 있음).

완료 기준: 등록된 issuer/subject/audience를 az identity federated-credential show로 확인합니다.

워크로드 배포 온프레미스

왜 하나요? 실제로 모델을 호출하는 파드를 배포해 WIF가 끝까지 동작하는지 봅니다. 5단계에서 설명한 projected 볼륨과 환경변수를 파드 매니페스트에 직접 넣습니다. 앞 단계와 맞물리는 부분은 ServiceAccount 이름(6단계 subject)과 토큰 audience입니다.

🔑 WIF 설정 포인트매니페스트에서 강조된 줄이 WIF 연결에 쓰입니다: SA 이름·네임스페이스(= Subject), projected 볼륨의 audience, AZURE_* 환경변수. 이 값들만 있으면 DefaultAzureCredential이 federated 토큰을 자동으로 사용합니다.

아래는 2단계의 셸 변수(FOUNDRY, MODEL, CLIENT_ID, TENANT_ID)가 설정된 셸에서 그대로 실행됩니다. 다른 셸이라면 해당 자리의 값을 직접 넣으세요. 예제 코드는 ConfigMap으로 넣고 공개 python 이미지에서 SDK를 설치해 실행하므로 이미지를 따로 빌드하지 않아도 됩니다(운영에서는 사내 이미지에 SDK를 포함).

kubectl apply -f - <<EOF
apiVersion: v1
kind: Namespace
metadata:
  name: wif-demo
---
# 1) ServiceAccount: Subject(6단계) — 어노테이션 불필요
apiVersion: v1
kind: ServiceAccount
metadata:
  name: wif-sa
  namespace: wif-demo
---
# 2) 예제 앱 코드 (아래 "앱 핵심 코드"와 동일)
apiVersion: v1
kind: ConfigMap
metadata:
  name: wif-app
  namespace: wif-demo
data:
  call.py: |
    import os
    from azure.identity import DefaultAzureCredential, get_bearer_token_provider
    from openai import AzureOpenAI
    credential = DefaultAzureCredential()
    token_provider = get_bearer_token_provider(
        credential, "https://cognitiveservices.azure.com/.default")
    client = AzureOpenAI(azure_endpoint=os.environ["FOUNDRY_ENDPOINT"], api_version="2024-10-21",
                         azure_ad_token_provider=token_provider)
    r = client.chat.completions.create(model=os.environ["FOUNDRY_DEPLOYMENT"], max_completion_tokens=500,
        messages=[{"role": "user", "content": "한국어로 짧게 인사해 주세요."}])
    print(r.choices[0].message.content)
---
# 3) Job: projected 토큰 볼륨 + AZURE_* 환경변수
apiVersion: batch/v1
kind: Job
metadata:
  name: wif-call
  namespace: wif-demo
spec:
  backoffLimit: 0
  template:
    spec:
      serviceAccountName: wif-sa
      restartPolicy: Never
      containers:
        - name: demo
          image: python:3.12-slim
          command: ["sh", "-c", "pip install -q azure-identity openai && python /app/call.py"]
          env:
            - name: FOUNDRY_ENDPOINT
              value: "https://$FOUNDRY.openai.azure.com"
            - name: FOUNDRY_DEPLOYMENT
              value: "$MODEL"
            - name: AZURE_CLIENT_ID
              value: "$CLIENT_ID"
            - name: AZURE_TENANT_ID
              value: "$TENANT_ID"
            - name: AZURE_AUTHORITY_HOST
              value: "https://login.microsoftonline.com/"
            - name: AZURE_FEDERATED_TOKEN_FILE
              value: /var/run/secrets/azure/tokens/azure-identity-token
          volumeMounts:
            - name: app
              mountPath: /app
            - name: azure-identity-token
              mountPath: /var/run/secrets/azure/tokens
              readOnly: true
      volumes:
        - name: app
          configMap:
            name: wif-app
        - name: azure-identity-token
          projected:
            sources:
              - serviceAccountToken:
                  audience: api://AzureADTokenExchange
                  expirationSeconds: 3600
                  path: azure-identity-token
EOF

kubectl -n wif-demo wait --for=condition=complete job/wif-call --timeout=300s
kubectl -n wif-demo logs job/wif-call

운영 시 고려사항

  • 서명 키 회전: JWKS에 이전·신규 키를 함께 게시하고 갱신을 자동화하세요. 게시 누락은 곧 인증 장애입니다.
  • issuer 호스팅 보호: 쓰기 권한을 최소화하세요. 이 파일을 바꿀 수 있는 사람은 임의 토큰을 신뢰하게 만들 수 있습니다. 읽기 전용 공개 + 변경 감사 로그를 권장합니다.
  • 가용성: issuer 호스팅이 내려가도 이미 발급된 액세스 토큰은 만료 전까지 동작하지만, 새 토큰 교환은 실패합니다.
  • 최소 권한: 워크로드(네임스페이스/SA)별 UAMI와 federated credential을 분리하고, UAMI 역할은 Cognitive Services OpenAI User 등 필요한 최소 범위로 제한합니다.
  • 다중 클러스터: 클러스터마다 issuer가 달라야 하며 각각 federated credential이 필요합니다.
  • Foundry 네트워크: 이 가이드는 공용 엔드포인트 기준입니다. Private Endpoint만 허용하려면 ExpressRoute/VPN, 사설 DNS가 추가로 필요합니다.
  • API Key 비활성: Foundry disableLocalAuth=true로 키 경로를 막아 WIF 외 우회를 차단합니다.
