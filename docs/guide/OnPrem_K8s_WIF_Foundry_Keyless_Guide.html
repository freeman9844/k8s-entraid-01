먼저 읽기: 무엇을 만들고, 왜 필요한가요?

Azure 안의 VM·AKS는 관리 ID로 토큰을 받지만, 온프레미스 파드는 그럴 수 없어 보통 Client Secret이나 인증서, API Key를 Secret에 저장합니다. 이 가이드는 그 대신 클러스터가 서명한 토큰을 Entra ID가 직접 검증하게 해 저장할 비밀을 없앱니다. 유출·만료·회전 관리가 필요한 값이 없어집니다.

용어이 구성에서 하는 일
Workload Identity Federation (WIF)외부 ID 공급자(여기서는 온프레미스 Kubernetes)가 발급한 토큰을 Entra ID가 신뢰하고 Azure 액세스 토큰으로 교환해 주는 기능
OIDC Issuer“이 토큰은 내 클러스터가 서명했다”를 증명하는 공개 주소. Entra가 여기서 discovery 문서와 JWKS(공개키)를 읽음
UAMI (사용자 할당 관리 ID)파드가 가장하게 될 Azure 쪽 ID. Foundry 권한을 가짐. VM이나 클러스터에 붙이는 것이 아니라 federated credential의 대상일 뿐임
Federated credentialUAMI에 붙이는 신뢰 규칙. issuer + subject + audience가 모두 일치하는 토큰만 교환
Workload Identity webhook라벨이 붙은 파드에 SA 토큰과 AZURE_* 환경변수를 자동 주입. 앱은 DefaultAzureCredential만 호출

★ WIF 신뢰 체인: 값 4개가 한 글자도 틀리지 않고 이어져야 합니다

“온프레미스 클러스터가 서명한 토큰”과 “Entra의 UAMI에 등록한 규칙”이 같은 값을 가리켜야 합니다. 아래 표의 같은 행은 문자 단위로 동일해야 하며 틀리면 Entra가 교환을 거부합니다. 3~6단계가 이 연결을 하나씩 만듭니다.

값토큰이 가진 값 (온프레미스 클러스터 발급)Entra에 등록한 값 (federated credential)설정 단계
Issuer클레임 iss = API 서버 --service-account-issuerissuer3단계 ↔ 6단계
Subject클레임 sub = system:serviceaccount:<네임스페이스>:<SA 이름>subject7단계 ↔ 6단계
Audience클레임 aud = api://AzureADTokenExchange (webhook이 주입)audiences5단계 ↔ 6단계
서명 키헤더 kid + RS256 서명 (클러스터 개인키)Entra가 issuer/.well-known/openid-configuration → jwks_uri에서 가져온 공개키3단계 ↔ 4단계

추가로 파드는 UAMI client ID(ServiceAccount 어노테이션)와 테넌트 ID를 알아야 하고, UAMI는 Foundry에 RBAC 권한을 가져야 합니다(2단계).

왜 하나요? 파드가 최종적으로 가장할 ID(UAMI), 호출 대상(Foundry), Entra가 읽을 issuer 호스팅 공간을 만듭니다.

RG=rg-wif-demo; LOC=eastus2; SUFFIX=$RANDOM
az group create -n $RG -l $LOC

# 1) UAMI: 파드가 가장할 Azure ID (비밀 없음)
az identity create -g $RG -n id-wif-demo
CLIENT_ID=$(az identity show -g $RG -n id-wif-demo --query clientId -o tsv)
PRINCIPAL_ID=$(az identity show -g $RG -n id-wif-demo --query principalId -o tsv)

# 2) Foundry(AIServices) 리소스 + 모델 배포는 포털 또는 랩 스크립트(01-azure-infra.sh) 참고
#    중요: API Key 비활성(disableLocalAuth=true)로 두면 keyless만 가능함을 증명할 수 있음

# 3) UAMI에 Foundry 호출 권한 (데이터 평면 역할, 최소 권한)
az role assignment create --assignee-object-id $PRINCIPAL_ID --assignee-principal-type ServicePrincipal \
  --role "Cognitive Services OpenAI User" --scope <Foundry 리소스 ID>

az storage account create -g $RG -n stwif$SUFFIX -l $LOC --sku Standard_LRS --allow-shared-key-access false
az storage blob service-properties update --account-name stwif$SUFFIX --static-website --auth-mode login
ISSUER_URL=$(az storage account show -g $RG -n stwif$SUFFIX --query primaryEndpoints.web -o tsv | sed 's:/*$::')
UAMI 대신 앱 등록?Entra 앱 등록(App registration)에도 federated credential을 만들 수 있습니다. 이 가이드는 별도 비밀·인증서 관리가 없고 Azure RBAC로 권한을 주기 쉬운 UAMI를 사용합니다.
ISSUER_URL끝에 슬래시를 붙이지 않은 값으로 통일합니다. 이후 3단계 플래그와 6단계 federated credential에 동일하게 사용합니다.
issuer 호스팅의 대안사내 공개 웹서버/CDN, GitHub Pages 등 Entra가 인터넷에서 읽을 수 있는 공인 HTTPS 주소면 됩니다. 사설 주소(사내 전용 DNS)는 Entra가 접근할 수 없어 사용할 수 없습니다.

Storage 공개 접근이 구독/관리그룹 정책으로 Disabled가 강제되면 issuer를 열 수 없습니다(4단계 경고 참고).

클러스터 API 서버에 OIDC issuer 지정 WIF 핵심 ① 온프레미스

왜 하나요? 클러스터가 발급하는 ServiceAccount 토큰의 iss가 Entra가 접근할 수 있는 공개 URL이 되게 합니다. 기본값(https://kubernetes.default.svc.cluster.local 등)은 외부에서 접근할 수 없어 WIF가 성립하지 않습니다.

--service-account-issuer토큰 iss 값. 6단계 federated credential의 issuer와 완전히 같아야 함
--service-account-jwks-uriAPI 서버가 discovery 문서에 노출하는 JWKS 위치. 4단계에서 이 주소에 파일이 올라가도록 $ISSUER_URL/openid/v1/jwks로 지정

k3s 랩 검증

kube-apiserver-arg:

  - "service-account-jwks-uri=https://stwif<SUFFIX>.z20.web.core.windows.net/openid/v1/jwks"

    - --service-account-issuer=<ISSUER_URL>
    - --service-account-jwks-uri=<ISSUER_URL>/openid/v1/jwks

이미 운영 중인 클러스터라면 (중요, 미검증): issuer를 바꾸면 기존 토큰의 iss가 달라져 그 토큰을 검증하던 기존 소비자가 깨질 수 있습니다. --service-account-issuer는 여러 번 지정할 수 있으며 첫 번째 값이 새 토큰 발급에 쓰이고 나머지는 검증에만 허용됩니다. 새 공개 issuer를 첫 번째로, 기존 issuer를 두 번째로 두면 기존 토큰이 계속 유효합니다. 적용 전에 kubectl get --raw /.well-known/openid-configuration으로 현재 issuer 값을 기록하세요. HA 컨트롤 플레인은 모든 노드에 같은 설정을 적용합니다.

완료 기준: kubectl get --raw /.well-known/openid-configuration의 issuer와 jwks_uri가 설정한 공개 URL로 나옵니다. (랩에서는 k3s 노드가 Ready가 되고 4단계 대조 검증이 통과하면 확인됨)

OIDC 메타데이터 공개 WIF 핵심 ② 온프레미스 → Azure

왜 하나요? Entra ID는 토큰의 iss 주소로 직접 접속해 서명 검증용 공개키를 가져옵니다. 클러스터 서명 키의 공개키만 JWKS로 만들어 공개 호스팅에 올립니다. 개인키는 클러스터 밖으로 나가지 않습니다.

4-1. 공개키(JWKS) 확보 — 방법 두 가지

방법설명상태
A. API 서버에서 가져오기
(배포판 무관)		kubectl get --raw /openid/v1/jwks > jwks.json
kubectl get --raw /.well-known/openid-configuration > openid-configuration
3단계에서 issuer/jwks-uri를 공개 URL로 지정했으므로 그대로 올리면 됩니다.		참고용 · 미검증
B. 서명 공개키 파일로 직접 생성컨트롤 플레인의 서명 키에서 공개키를 추출해 JWKS 변환. k3s 경로: /var/lib/rancher/k3s/server/tls/service.current.key, service.key(키 회전 시 이전 키도 포함). 변환 스크립트: scripts/lib/make_jwks.py (kid는 DER SPKI의 SHA-256을 base64url 인코딩, Kubernetes와 동일)랩 검증

키 회전 시 JWKS에 이전 키와 새 키가 함께 있어야 이미 발급된 토큰이 계속 검증됩니다. 회전 때마다 이 단계를 다시 수행하는 운영 절차를 마련하세요(10단계).

4-2. 업로드 경로

/.well-known/openid-configurationEntra가 가장 먼저 읽는 문서. issuer가 토큰의 iss와 같아야 함
/openid/v1/jwks서명 검증용 공개키 목록. 토큰 헤더의 kid와 일치하는 키가 있어야 함
{
  "issuer": "https://stwif<SUFFIX>.z20.web.core.windows.net",
  "jwks_uri": "https://stwif<SUFFIX>.z20.web.core.windows.net/openid/v1/jwks",
  "response_types_supported": ["id_token"],
  "subject_types_supported": ["public"],
  "id_token_signing_alg_values_supported": ["RS256"]
}

az storage blob upload --account-name stwif$SUFFIX --auth-mode login -c '$web' \

az storage blob upload --account-name stwif$SUFFIX --auth-mode login -c '$web' \
  -f jwks.json -n openid/v1/jwks --content-type application/json --overwrite

4-3. 대조 검증 (필수)

실제 토큰의 iss·kid가 공개된 값과 같은지 확인합니다. 랩 스크립트 03-publish-oidc.sh는 이 대조(scripts/lib/check_jwks.py)까지 수행합니다.

curl -fsS $ISSUER_URL/.well-known/openid-configuration
curl -fsS $ISSUER_URL/openid/v1/jwks
kubectl -n default create token default --audience api://AzureADTokenExchange   # iss / kid 비교 대상

완료 기준(랩): OK: 토큰의 iss/kid 가 공개된 issuer/JWKS 와 일치합니다

정책 때문에 업로드/접근이 막히면: 일부 구독은 정책(modify 효과)이 Storage의 publicNetworkAccess를 Disabled로 강제하고 CLI로 바꿔도 되돌립니다. 랩 환경에서는 관리그룹의 MCAPSGovDeployPolicies가 원인이었고, 리소스 그룹 범위 정책 예외 생성 → 1분 대기 → 공개 접근 활성화 후 통과했습니다. 
az policy state list --resource $(az storage account show -g $RG -n stwif$SUFFIX --query id -o tsv) \
  --query "[?policyDefinitionAction=='modify'].{a:policyAssignmentName,d:policyDefinitionName,scope:policyAssignmentScope}" -o table

az policy exemption create --name wif-demo-storage --policy-assignment "<할당 ID>" \
  --exemption-category Waiver --resource-group $RG --expires-on "<UTC 시각>"

az storage account update -g $RG -n stwif$SUFFIX --public-network-access Enabled --default-action Allow
예외를 받을 수 없으면 issuer를 사내 공개 웹서버/CDN, GitHub Pages 등 다른 공인 HTTPS 호스팅에 올리고 ISSUER_URL을 바꿔 3단계부터 다시 진행합니다.

Workload Identity webhook 설치 WIF 핵심 ③ 온프레미스

왜 하나요? 파드가 Entra에 제시할 토큰(audience api://AzureADTokenExchange인 SA 토큰)과 접속 정보를 자동으로 파드에 넣어 줍니다. 이 webhook은 Azure 밖의 Kubernetes에서도 동작합니다.

helm repo add azure-workload-identity https://azure.github.io/azure-workload-identity/charts
helm repo update
helm upgrade --install workload-identity-webhook azure-workload-identity/workload-identity-webhook \
  --namespace azure-workload-identity-system --create-namespace \
  --set azureTenantID=<TENANT_ID> --wait --timeout 5m
kubectl -n azure-workload-identity-system get pods

webhook이 파드에 주입하는 것

파드에 라벨 azure.workload.identity/use: "true"가 있으면 다음이 자동 주입됩니다.

AZURE_FEDERATED_TOKEN_FILE토큰 파일 경로(/var/run/secrets/azure/wi/.../azure-identity-token)
projected 볼륨audience가 api://AzureADTokenExchange인 SA 토큰(Audience 연결 고리). kubelet이 만료 전 자동 갱신

주입 값은 모두 비밀이 아닙니다(ID와 경로). 토큰은 짧은 수명의 파드 전용 값이며 Secret 오브젝트로 저장되지 않습니다. 사내 레지스트리만 허용하는 환경이면 webhook 이미지를 미러링하고 Helm 값으로 이미지 경로를 바꾸세요(미검증).

완료 기준: azure-wi-webhook-controller-manager 파드 2개가 Running입니다. 인증서 준비 중 재시작 1회는 정상입니다.

Federated credential 생성 WIF 핵심 ④ · 가장 중요 Azure

왜 하나요? “어느 issuer의 어느 ServiceAccount가 보낸 토큰을 이 UAMI로 인정할지”를 Entra에 등록합니다. 온프레미스 클러스터가 Azure 리소스에 접근할 수 있는 근거가 이 규칙 하나입니다.

az identity federated-credential create \
  -g $RG --identity-name id-wif-demo -n fic-onprem-wif-sa \
  --issuer   "$ISSUER_URL" \
  --subject  "system:serviceaccount:wif-demo:wif-sa" \
  --audiences api://AzureADTokenExchange
파라미터값과 의미
--issuerISSUER_URL. 토큰 iss와 문자 단위로 동일(끝 슬래시 없음). 다르면 AADSTS700211
--subjectsystem:serviceaccount:<네임스페이스>:<SA 이름>. 정확히 일치(와일드카드 불가)
--audiencesapi://AzureADTokenExchange. 토큰 aud와 일치해야 함

subject를 SA 하나로 제한하는 이유 (최소 권한)

subject를 wif-sa로 고정하면 같은 클러스터의 다른 ServiceAccount는 UAMI 권한을 쓸 수 없습니다. 랩에서 wif-other-sa에 같은 client-id 어노테이션을 붙여도 Entra가 AADSTS700213으로 거부함을 확인했습니다. 워크로드마다 UAMI와 federated credential을 분리하세요.

등록 직후 전파에 수 분 걸릴 수 있습니다. 랩 검증 스크립트는 자동 재시도합니다. 클러스터를 여러 개 운영한다면 클러스터마다 issuer가 다르므로 federated credential을 각각 만들어야 합니다(UAMI당 한도 있음).

완료 기준: 등록된 issuer/subject/audience를 az identity federated-credential show로 확인합니다. 포털: Managed Identities → id-wif-demo → Federated credentials

왜 하나요? 실제로 모델을 호출하는 파드를 배포해 WIF가 끝까지 동작하는지 봅니다. 앞 단계와 맞물리는 부분은 ServiceAccount와 파드 라벨 두 곳입니다.

WIF 심화 점검: 연결 고리를 하나씩 직접 확인 선택 · 디버깅용

검증이 실패하거나 원리를 눈으로 확인하고 싶을 때 신뢰 체인을 한 고리씩 점검합니다. 아래 명령은 가이드 보조용이며 랩 검증 스크립트에는 포함되어 있지 않습니다.

9-1. 토큰이 가진 값 (Issuer · Subject · Audience)

kubectl -n wif-demo create token wif-sa --audience api://AzureADTokenExchange \
 | cut -d. -f2 | tr '_-' '/+' | awk '{print $0 "=="}' | base64 -d 2>/dev/null | python3 -m json.tool

9-2. Entra에 등록된 값

az identity federated-credential list -g $RG --identity-name id-wif-demo \
  --query "[].{name:name,issuer:issuer,subject:subject,aud:audiences}" -o jsonc

9-3. 공개 issuer 문서 (Entra 관점)

curl -s $ISSUER_URL/.well-known/openid-configuration | python3 -m json.tool
curl -s $ISSUER_URL/openid/v1/jwks | python3 -m json.tool   # keys[].kid 가 9-1 토큰 헤더의 kid 와 같아야 함

9-4. 토큰 교환을 수동으로 재현

webhook과 SDK가 대신 해 주는 일을 직접 합니다. SA 토큰을 client_assertion으로 제출하면 Entra가 액세스 토큰을 돌려줍니다. 미검증

SA_TOKEN=$(kubectl -n wif-demo create token wif-sa --audience api://AzureADTokenExchange)
curl -s -X POST "https://login.microsoftonline.com/$TENANT_ID/oauth2/v2.0/token" \
  -d "client_id=$CLIENT_ID" \
  -d "grant_type=client_credentials" \
  -d "scope=https://cognitiveservices.azure.com/.default" \
  -d "client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer" \
  --data-urlencode "client_assertion=$SA_TOKEN" | python3 -m json.tool

client_secret이나 인증서를 전혀 보내지 않는 점에 주목하세요. 다른 SA 토큰을 넣으면 AADSTS700213이 나옵니다.

어느 고리에서 깨지는가

오류끊어진 고리확인 · 조치

운영 시 고려사항

  • 서명 키 회전: JWKS에 이전·신규 키를 함께 게시하고 갱신을 자동화하세요. 게시 누락은 곧 인증 장애입니다.
  • issuer 호스팅 보호: 쓰기 권한을 최소화하세요. 이 파일을 바꿀 수 있는 사람은 임의 토큰을 신뢰하게 만들 수 있습니다. 읽기 전용 공개 + 변경 감사 로그를 권장합니다.
  • 가용성: issuer 호스팅이 내려가도 이미 발급된 액세스 토큰은 만료 전까지 동작하지만, 새 토큰 교환은 실패합니다.
  • 최소 권한: 워크로드(네임스페이스/SA)별 UAMI와 federated credential을 분리하고, UAMI 역할은 Cognitive Services OpenAI User 등 필요한 최소 범위로 제한합니다.
  • 다중 클러스터: 클러스터마다 issuer가 달라야 하며 각각 federated credential이 필요합니다.
  • Foundry 네트워크: 이 가이드는 공용 엔드포인트 기준입니다. Private Endpoint만 허용하려면 ExpressRoute/VPN, 사설 DNS가 추가로 필요합니다.
  • API Key 비활성: Foundry disableLocalAuth=true로 키 경로를 막아 WIF 외 우회를 차단합니다.
