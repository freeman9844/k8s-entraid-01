인증서 구성 가장 중요양쪽

신뢰 관계는 인증서 한 쌍으로 성립합니다. 개인키는 파드에만, 공개 인증서는 Entra에만 있습니다.

구성 요소위치 / 값
개인키 + 인증서 (PEM)Kubernetes Secret wif-cert → 파드 /var/run/cert/cert.pem
공개 인증서 (.crt)Entra 앱 등록 → 인증서 및 비밀 (키 자격 증명)
매칭 기준assertion 헤더의 thumbprint(x5t)와 등록된 키의 일치 여부
필수 환경변수AZURE_CLIENT_ID, AZURE_TENANT_ID, AZURE_CLIENT_CERTIFICATE_PATH

인증서 생성 (openssl, 자체 서명, RSA 2048, 3년)

bash
openssl req -x509 -newkey rsa:2048 -nodes -sha256 -days 1095 -subj "/CN=app-wif-cert" \  -keyout client.key -out client.crt\ncat client.key client.crt > client.pem && rm client.key\nopenssl x509 -in client.crt -noout -fingerprint -sha1   # thumbprint 확인
# client.pem = 개인키 + 인증서 (파드용)   client.crt = 공개 인증서 (Entra 업로드용)

운영에서는 사내 CA 또는 Key Vault가 발급한 인증서를 사용하세요. 자체 서명도 Entra 키 자격 증명으로는 동작합니다(랩에서 검증).

Azure 구성 Azure

bash
# 1) 앱 등록 + 서비스 주체
APP_ID=$(az ad app create --display-name app-wif-cert --query appId -o tsv)
az ad sp create --id $APP_ID

# 2) 공개 인증서만 업로드
az ad app credential reset --id $APP_ID --cert @client.crt --append

# 3) Foundry 호출 권한 (Foundry 는 disableLocalAuth=true 로 키 차단)
az role assignment create --assignee-object-id $(az ad sp show --id $APP_ID --query id -o tsv) \
  --assignee-principal-type ServicePrincipal \
  --role "Cognitive Services OpenAI User" --scope $FOUNDRY_ID

자동화: AUTH_MODE=cert bash scripts/01-azure-infra.sh 후 scripts/c1-create-app-cert.sh.

앱 등록은 리소스 그룹 밖(테넌트)에 생성됩니다. 정리할 때 az ad app delete가 별도로 필요합니다(99-cleanup.sh가 처리).

Kubernetes 구성 온프레미스

Secret 하나와 볼륨 마운트, 환경변수 3개면 충분합니다.

bash
kubectl create namespace wif-demo
kubectl -n wif-demo create secret generic wif-cert --from-file=cert.pem=client.pem
yaml
env:
  - {name: AZURE_CLIENT_ID,   value: "<앱 등록 appId>"}
  - {name: AZURE_TENANT_ID,   value: "<테넌트 ID>"}
  - {name: AZURE_CLIENT_CERTIFICATE_PATH, value: /var/run/cert/cert.pem}
volumeMounts:
  - {name: cert, mountPath: /var/run/cert, readOnly: true}
volumes:
  - name: cert
    secret: {secretName: wif-cert}

테스트에 사용한 전체 매니페스트 (Deployment)

검증에 사용한 매니페스트입니다(k8s/deploy-cert.yaml.tpl).

yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cert-call
  namespace: wif-demo
spec:
  replicas: 1
  selector:
    matchLabels:
      app: cert-call
  template:
    metadata:
      labels:
        app: cert-call
    spec:
      containers:
        - name: demo
          image: python:3.12-slim
          command: ["sh", "-c", "pip install -q --disable-pip-version-check azure-identity openai && python /app/demo_cert.py; sleep infinity"]
          env:
            - name: AZURE_CLIENT_ID
              value: "<앱 등록 appId>"
            - name: AZURE_TENANT_ID
              value: "<테넌트 ID>"
            - name: AZURE_CLIENT_CERTIFICATE_PATH
              value: /var/run/cert/cert.pem
            - name: FOUNDRY_ENDPOINT
              value: "https://<foundry 이름>.openai.azure.com"
            - name: FOUNDRY_DEPLOYMENT
              value: "gpt-5.4-mini"
            - name: TOKEN_RETRIES
              value: "6"
          volumeMounts:
            - name: app
              mountPath: /app
            - name: cert
              mountPath: /var/run/cert
              readOnly: true
      volumes:
        - name: app
          configMap:
            name: cert-demo-app      # demo_cert.py 를 담은 ConfigMap
        - name: cert
          secret:
            secretName: wif-cert     # 개인키+인증서 PEM

FOUNDRY_*, TOKEN_RETRIES, ConfigMap, 끝의 sleep infinity(결과 로그 확인용)는 테스트 데모 앱용입니다. 실제 앱에는 인증서 관련 환경변수 3개, cert 볼륨 마운트, cert 볼륨만 필요합니다.

Secret은 기본적으로 base64일 뿐입니다. etcd 암호화(--secrets-encryption)와 RBAC 최소화를 반드시 적용하세요.

인증서 갱신(회전) E2E 검증

Entra 앱 등록은 공개 인증서를 여러 개 동시에 등록할 수 있으므로, 새 인증서를 추가한 뒤 교체하고 옛 인증서를 삭제하면 무중단으로 갱신됩니다. 아래 절차는 scripts/c4-rotate-cert.sh로 실제 검증했습니다.

bash
# 1) 새 인증서 생성 (90일)
bash scripts/lib/make_cert.sh app-wif-cert 90 .state/cert-new client

# 2) Entra 에 추가 (반드시 --append: 없으면 기존 키가 모두 사라짐)
OLD_KEY_ID=$(az ad app credential list --id $APP_ID --cert --query "[0].keyId" -o tsv)
az ad app credential reset --id $APP_ID --cert @.state/cert-new/client.crt --append

# 3) Secret 덮어쓰기 + 파드 재시작
kubectl -n <ns> create secret generic wif-cert --from-file=cert.pem=.state/cert-new/client.pem \
  --dry-run=client -o yaml | kubectl apply -f -
kubectl -n <ns> rollout restart deployment/<name>
kubectl -n <ns> rollout status deployment/<name>

# 4) 새 인증서로 호출 성공을 확인한 뒤 옛 키 삭제 (인증서 키는 --cert 필요)
az ad app credential delete --id $APP_ID --cert --key-id $OLD_KEY_ID

  • Secret 덮어쓰기: 같은 이름의 Secret 데이터가 교체됩니다. 볼륨 마운트 파일은 kubelet이 자동 갱신하지만 앱이 시작 시 한 번만 읽을 수 있으므로 재시작을 권장합니다. subPath 마운트나 환경변수 주입은 자동 갱신되지 않습니다.
  • 수명: 유출 영향 범위를 줄이려면 90일~1년 인증서와 자동 회전(cert-manager 등 사내 CA 연동)을 권장합니다. 갱신된 공개 인증서를 Entra에 올리는 작업은 별도 자동화가 필요합니다.

개인키 보호 미검증/참고용

  • Key Vault + CSI Driver: Azure Arc 등으로 Key Vault에 접근 가능하면 개인키를 Secret 대신 Key Vault에서 마운트할 수 있습니다. 단 Key Vault 접근 자체에 또 다른 자격 증명이 필요한 순환 구조에 유의하세요.
  • HSM/TPM: 개인키를 추출 불가능하게 보관하려면 노드 TPM 또는 HSM 기반 서명 구성을 별도 검토하세요.
