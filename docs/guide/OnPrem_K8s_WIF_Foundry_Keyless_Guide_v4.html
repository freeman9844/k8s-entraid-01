먼저 읽기: 무엇을 만들고, 왜 필요한가요?

Azure 안의 VM·AKS는 관리 ID로 토큰을 받지만, 온프레미스 파드는 그럴 수 없어 보통 Client Secret이나 API Key를 Secret에 저장합니다. 이 가이드는 클러스터가 서명한 토큰을 Entra ID가 직접 검증하게 해 저장할 비밀을 없앱니다.

용어이 구성에서 하는 일
Workload Identity Federation (WIF)외부 ID 공급자(여기서는 k3s)가 발급한 토큰을 Entra ID가 신뢰하고 Azure 액세스 토큰으로 교환해 주는 기능
OIDC Issuer“이 토큰은 내 클러스터가 서명했다”를 증명하는 공개 주소. Entra가 여기서 discovery 문서와 JWKS(공개키)를 읽음
UAMI파드가 가장할 Azure 쪽 ID. Foundry 권한을 가지며, VM에 붙이지 않고 federated credential의 대상으로만 사용
Federated credentialUAMI에 붙이는 신뢰 규칙. issuer + subject + audience가 모두 일치하는 토큰만 교환
Projected SA 토큰파드 매니페스트의 serviceAccountToken 볼륨. audience가 api://AzureADTokenExchange인 토큰을 kubelet이 파일로 넣고 갱신. 앱은 DefaultAzureCredential만 호출

k3s 설치: API 서버 issuer 플래그 1개 WIF 핵심 ① 관리 VM

k3s 설치 시 service-account-issuer를 3단계에서 만든 공개 URL로 지정합니다. 이 값이 ServiceAccount 토큰의 iss가 됩니다.

🔑 WIF 설정 포인트강조된 줄 service-account-issuer 값 = 토큰의 Issuer = 6단계 --issuer. 끝에 /를 붙이거나 http로 쓰는 등 한 글자만 달라도 AADSTS700211이 납니다.

왜 하나요? Entra는 토큰의 iss 주소로 찾아가 서명 검증용 공개키를 가져옵니다. 기본값(https://kubernetes.default.svc)은 외부에서 접근할 수 없으므로, 외부에서 읽을 수 있는 URL로 바꿔야 합니다. API 서버가 이 값으로 토큰을 서명하며, 개인키는 클러스터 밖으로 나가지 않습니다. 토큰이 발급되기 전에 설정해야 하며, 이미 발급된 토큰의 iss는 바뀌지 않습니다.

source ~/wif.env
sudo mkdir -p /etc/rancher/k3s
sudo tee /etc/rancher/k3s/config.yaml >/dev/null <<EOF
write-kubeconfig-mode: "0644"
kube-apiserver-arg:
  - "service-account-issuer=${ISSUER_URL}"
EOF
# GitHub 릴리스 다운로드가 일시적으로 504를 내므로 재시도하고, 설치 로그는 파일로 남깁니다
for i in 1 2 3 4 5; do
  curl -sfL https://get.k3s.io | INSTALL_K3S_CHANNEL=v1.36 sudo -E sh - >/tmp/k3s-install.log 2>&1 && break
  echo "k3s 설치 재시도($i): $(tail -1 /tmp/k3s-install.log)"; sleep 20
done
mkdir -p ~/.kube && sudo cp /etc/rancher/k3s/k3s.yaml ~/.kube/config && sudo chown $(id -u):$(id -g) ~/.kube/config
echo 'export KUBECONFIG=$HOME/.kube/config' >> ~/wif.env
export KUBECONFIG=$HOME/.kube/config
until kubectl get nodes 2>/dev/null | grep -q ' Ready'; do sleep 3; done
kubectl get nodes
kubectl get --raw /.well-known/openid-configuration; echo

완료 확인: 노드 Ready, 그리고 discovery 문서의 issuer가 ISSUER_URL과 같음(jwks_uri는 내부 주소로 보이는 것이 정상이며 5단계에서 해결).

OIDC 메타데이터 공개 WIF 핵심 ② 관리 VM → Storage

API 서버의 공개키(JWKS)를 가져오고, jwks_uri가 공개 주소를 가리키는 discovery 문서를 직접 만들어 함께 업로드합니다. 경로와 Content-Type: application/json이 중요합니다.

🔑 WIF 설정 포인트
강조 줄의미
issuer4단계 issuer와 동일해야 함
jwks_uriEntra가 공개키를 가져가는 공개 주소(내부 주소 불가)
업로드 경로.well-known/openid-configuration, openid/v1/jwks 고정

왜 하나요? Entra는 <issuer>/.well-known/openid-configuration을 읽고, 그 안의 jwks_uri에서 공개키를 가져와 토큰 서명을 검증합니다. k3s가 만드는 discovery 문서는 jwks_uri가 내부 주소(https://10.x.x.x:6443/...)라서 그대로 올리면 Entra가 읽지 못합니다. 그래서 discovery 문서는 직접 만들고, JWKS는 API 서버에서 가져옵니다. 공개키만 올라가며 개인키는 업로드되지 않습니다. 서명 키가 바뀌면(클러스터 재구축 등) JWKS를 다시 올려야 합니다.

source ~/wif.env
mkdir -p ~/oidc && cd ~/oidc
kubectl get --raw /openid/v1/jwks > jwks.json
cat > openid-configuration <<EOF
{
  "issuer": "$ISSUER_URL",
  "jwks_uri": "$ISSUER_URL/openid/v1/jwks",
  "response_types_supported": ["id_token"],
  "subject_types_supported": ["public"],
  "id_token_signing_alg_values_supported": ["RS256"]
}
EOF
az storage blob upload --account-name $ST --auth-mode login -c '$web' \
  -f openid-configuration -n .well-known/openid-configuration --content-type application/json --overwrite -o none
az storage blob upload --account-name $ST --auth-mode login -c '$web' \
  -f jwks.json -n openid/v1/jwks --content-type application/json --overwrite -o none

5-1. 공개 문서와 토큰 대조 검증 · 공통

curl -fsS $ISSUER_URL/.well-known/openid-configuration; echo
PUB_KIDS=$(curl -fsS $ISSUER_URL/openid/v1/jwks | jq -r '.keys[].kid')
TOKEN=$(kubectl -n default create token default --audience api://AzureADTokenExchange)
TOKEN_ISS=$(echo "$TOKEN" | cut -d. -f2 | tr '_-' '/+' | awk '{print $0 "=="}' | base64 -d 2>/dev/null | jq -r .iss)
TOKEN_KID=$(echo "$TOKEN" | cut -d. -f1 | tr '_-' '/+' | awk '{print $0 "=="}' | base64 -d 2>/dev/null | jq -r .kid)
echo "token iss=$TOKEN_ISS"; echo "token kid=$TOKEN_KID"; echo "public kids=$PUB_KIDS"
[ "$TOKEN_ISS" = "$ISSUER_URL" ] && echo "$PUB_KIDS" | grep -qx "$TOKEN_KID" && echo "OK: iss/kid 일치"

완료 확인: OK: iss/kid 일치.

옵션반드시 일치해야 하는 값
--issuer4단계 ISSUER_URL
--subjectsystem:serviceaccount:<네임스페이스>:<SA 이름> — 7단계 wif-demo/wif-sa
--audiencesapi://AzureADTokenExchange — 7단계 projected 볼륨 audience

왜 하나요? Entra는 issuer + subject + audience가 모두 일치하는 토큰에만 UAMI의 액세스 토큰을 발급합니다. subject를 특정 ServiceAccount로 좁혔기 때문에 같은 클러스터의 다른 파드나 다른 SA는 이 ID를 사용할 수 없습니다. 이 규칙이 Client Secret이나 인증서를 대신합니다. 등록 후 az identity federated-credential list -g $RG --identity-name id-wif-demo -o table로 확인할 수 있습니다.

source ~/wif.env
az identity federated-credential create -g $RG --identity-name id-wif-demo -n fic-onprem-wif-sa \
  --issuer "$ISSUER_URL" --subject "system:serviceaccount:wif-demo:wif-sa" \
  --audiences api://AzureADTokenExchange --query "{issuer:issuer,subject:subject}" -o json

subject의 네임스페이스·SA 이름(wif-demo, wif-sa)은 7단계 매니페스트와 문자 단위로 같아야 합니다. 다르면 AADSTS700213이 납니다.

워크로드 배포: 토큰 주입 + Foundry 호출 관리 VM (k3s)

Namespace, ServiceAccount, 호출 코드, Job을 한 번에 적용합니다. webhook 없이 projected 볼륨과 환경변수 4개로 DefaultAzureCredential이 토큰을 읽습니다. Secret은 만들지 않습니다.

🔑 WIF 설정 포인트매니페스트에서 강조된 줄이 WIF 연결에 쓰입니다. SA 이름·네임스페이스(= Subject), projected 볼륨의 audience, 그리고 AZURE_CLIENT_ID(UAMI) · AZURE_TENANT_ID · AZURE_FEDERATED_TOKEN_FILE(토큰 파일 경로, 볼륨 마운트 경로와 일치) 환경변수입니다. 이 값들만 있으면 DefaultAzureCredential이 federated 토큰을 자동으로 사용합니다.

동작 순서: ① kubelet이 audience api://AzureADTokenExchange인 SA 토큰을 파일(azure-identity-token)로 주입하고 주기적으로 갱신 → ② DefaultAzureCredential이 환경변수(AZURE_FEDERATED_TOKEN_FILE 등)를 보고 그 토큰을 Entra에 제시 → ③ Entra가 5단계의 공개키로 서명을 검증하고 6단계 규칙과 대조한 뒤 액세스 토큰 발급 → ④ 그 토큰으로 Foundry 호출. 앱 코드에는 비밀 값이 없습니다.

kubectl apply -f - <<EOF
apiVersion: v1
kind: Namespace
metadata:
  name: wif-demo
---
# 1) ServiceAccount: Subject(6단계) — 어노테이션 불필요
apiVersion: v1
kind: ServiceAccount
metadata:
  name: wif-sa
  namespace: wif-demo
---
# 2) 예제 앱 코드 (아래 "앱 핵심 코드"와 동일)
apiVersion: v1
kind: ConfigMap
metadata:
  name: wif-app
  namespace: wif-demo
data:
  call.py: |
    import os
    from azure.identity import DefaultAzureCredential, get_bearer_token_provider
    from openai import AzureOpenAI
    credential = DefaultAzureCredential()
    token_provider = get_bearer_token_provider(
        credential, "https://cognitiveservices.azure.com/.default")
    client = AzureOpenAI(azure_endpoint=os.environ["FOUNDRY_ENDPOINT"], api_version="2024-10-21",
                         azure_ad_token_provider=token_provider)
    r = client.chat.completions.create(model=os.environ["FOUNDRY_DEPLOYMENT"], max_completion_tokens=500,
        messages=[{"role": "user", "content": "한국어로 짧게 인사해 주세요."}])
    print(r.choices[0].message.content)
---
# 3) Job: projected 토큰 볼륨 + AZURE_* 환경변수
apiVersion: batch/v1
kind: Job
metadata:
  name: wif-call
  namespace: wif-demo
spec:
  backoffLimit: 0
  template:
    spec:
      serviceAccountName: wif-sa
      restartPolicy: Never
      containers:
        - name: demo
          image: python:3.12-slim
          command: ["sh", "-c", "pip install -q azure-identity openai && python /app/call.py"]
          env:
            - name: FOUNDRY_ENDPOINT
              value: "https://$FOUNDRY.openai.azure.com"
            - name: FOUNDRY_DEPLOYMENT
              value: "$MODEL"
            - name: AZURE_CLIENT_ID
              value: "$CLIENT_ID"
            - name: AZURE_TENANT_ID
              value: "$TENANT_ID"
            - name: AZURE_AUTHORITY_HOST
              value: "https://login.microsoftonline.com/"
            - name: AZURE_FEDERATED_TOKEN_FILE
              value: /var/run/secrets/azure/tokens/azure-identity-token
          volumeMounts:
            - name: app
              mountPath: /app
            - name: azure-identity-token
              mountPath: /var/run/secrets/azure/tokens
              readOnly: true
      volumes:
        - name: app
          configMap:
            name: wif-app
        - name: azure-identity-token
          projected:
            sources:
              - serviceAccountToken:
                  audience: api://AzureADTokenExchange
                  expirationSeconds: 3600
                  path: azure-identity-token
EOF

kubectl -n wif-demo wait --for=condition=complete job/wif-call --timeout=300s
kubectl -n wif-demo logs job/wif-call
